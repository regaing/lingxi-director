## 1. 需求概述

- **背景**：项目 v0.3.0 已能跑通「节点画布 → 提交 → 轮询 → 预览下载」主链路，但存在 10 项结构性短板（上游单点、协作缺失、并发弱、剪辑为零等），影响其在真实创作场景中的可用性。
- **目标**：按「代价 / 收益」排序补齐短板，让项目从「能跑」到「能交付成片」。
- **范围**：仅本仓库后端 `server.mjs` / `runner.mjs` / `lib/*`、前端 `web/src/*`。
- **非目标（明确不做）**：
  1. **不做多用户 / 账号 / 权限 / 多租户** —— 部署形态锁定单机本地（用户已确认），因此「协作缺失」这条短板**不补**，转为做「单机多标签页并发安全」这类必要防护。
  2. **不引入本地 GPU 推理** —— 不装 Python / CUDA / 模型权重，保持「`npm install` 即可跑」的核心优势。
  3. **不做完整时间轴剪辑** —— 不把项目变成剪映/PR，剪辑只做到「成片交付前的最小加工」。

## 2. 现状分析

### 2.1 与短板直接相关的代码事实（已核对源码）

| 短板 | 证据 |
|---|---|
| 上游单点 | `web/src/graph/model.js` 的 `PROVIDER` 常量硬编码 `name/baseUrl/resolutions/durationRange/ratios/framesVsRef/imageRatioMin/Max`；`server.mjs` 的 `gateway(pathname,{method,body})` 是唯一出口 |
| 无重试 | `gateway()` 只做一次 `fetch` + `res.text()`，无退避、无重试，429/503 原样抛给前端 |
| 并发弱 | `runner.mjs:431` 用 `activeByWf` Map 卡死「同流 1 run」；无队列、无并发度控制、无批量入口 |
| 素材笨重 | `runner.mjs` 组装 content 时图片/视频/音频**一律** `dataUrl`（base64）；`MAX_BODY` = 200MB；但 `lib/media-tools.mjs` 已有 `toDataUri` / `dataUriToFile` / `toLocalPath`，具备改 URL 的现成接口 |
| 数据寿命 | 网关任务只留 7 天；下载是带签名 CDN 链接；`lib/runs.mjs` 的 `KEEP_PER_WF = 50`，超 50 条直接删——老任务再也反查不出来 |
| 音频空白 | 无音频生成节点，`media.audio` 只能作输入；输出是否有音轨**未验证** |
| 剪辑为零 | 处理节点只有 `video.frame` / `video.concat` / `image.fit` / `video.info`，无字幕/配乐/转场/调色 |
| 模板生态 | `web/src/presets.js` 只有 13 条文本预设；`lib/bundle.mjs` 已有完整 zip 打包能力可复用 |
| 上手门槛 | 需 Node ≥22 + `npm run build` + 手写 `config.json` |
| 格式不通用 | 图为自定义结构，不兼容 ComfyUI 工作流 JSON |

### 2.2 技术栈

| 层次 | 技术 |
|---|---|
| 运行时 | Node ≥ 22（`node:sqlite` 内置） |
| 后端 | 仅 Node 内置模块 + `fflate`（zip） |
| 前端 | React 18 + `@xyflow/react` + Vite 5 |
| 数据库 | SQLite（`data/workbench.db`，WAL） |
| 媒体 | `@ffmpeg-installer/ffmpeg` + `@ffprobe-installer/ffprobe`（懒加载） |
| 上游 | 秘塔 H3，协议同构 MiniMax `/v2` |

### 2.3 全局约束（所有阶段必须遵守）

1. **只走 npm 依赖**，不引需要联网下载二进制或需要外部服务（Redis / Docker / 对象存储）的包
2. **保持单机可跑**，新增能力必须「缺省不启用也能跑」
3. UI 文案走 `web/src/i18n.jsx`；接口/行为变更同步 `CHANGELOG.md` 与 `AGENTS.md`
4. 图写入仍走 `wfStore` + revision 乐观锁，不走旁路

## 3. 路线图（按代价/收益排序）

### 批次 0 · 先验事实（0.5 人天，零风险）

**不改代码，只做实测**。结论决定后面几个阶段能不能成立：

| 验证项 | 方法 | 影响 |
|---|---|---|
| 输出视频有无音轨 | 用 `video.info` 探针跑一个真实产物，看 `streams` 里有无 `codec_type=audio` | 决定「音频」阶段是做配音还是做混音 |
| 首尾帧 + 参考素材能否同传 | 构造一次双输入的 `gen.video` 请求实测 | 若放行 → 解除 `PROVIDER.framesVsRef` 互斥，直接解锁一个能力（成本≈0） |
| 网关是否接受公网 URL 素材 | 把一张图挂公网地址塞进 `image_url.url` 实测 | 决定「素材瘦身」是做 URL 直传，还是只能优化 base64 内存占用 |
| 2K + 再生成的实际边界 | 补测 `duration` 与 `source_task_id`/`content` 组合 | 校准 `PROVIDER` 约束，减少 2013 误报 |

> **为什么排第一**：三条里有两条可能直接推翻某个阶段的设计。先花半天验，比做完发现方向错了便宜一个数量级。

---

### 批次 1 · 地基修补（约 5 人天，🟢 低复杂度）

**目标**：不动架构，先解决「跑长流程会掉链子」的三个点。

#### 1.1 上游调用加退避重试
- **位置**：`server.mjs` 的 `gateway()`
- **做法**：对 `429 / 502 / 503 / 504` 做指数退避（如 1s → 2s → 4s，最多 3 次），只对**幂等**请求（GET / 查询）默认开启；创建任务类 POST **不自动重试**（防重复扣费），改为向用户明确提示
- **收益**：消灭「渠道满要人工重试」这条已知限制
- **风险点**：POST 重试会导致重复计费，必须严格区分

#### 1.2 产物与任务快照归档
- **新增** `lib/archive.mjs`；**修改** `lib/runs.mjs`
- **做法**：
  - run 结束时把 `task_id` / `status` / `video_url` / 耗时 / 计费落一张 `run_outputs` 表，**不随 `KEEP_PER_WF=50` 删除**（run 删了，产物索引还在）
  - 可选开关：run 成功后自动把产物拉进 `downloads/`（对抗签名链接过期）
  - `GET /api/tasks?wfId=` 的过滤逻辑补一路：从 `run_outputs` 反查，不再受 50 条限制
- **收益**：直接消掉「任务 7 天过期 / 链接失效 / 老任务查不到」三条限制
- **数据变更**：新增表 `run_outputs(id, wf_id, run_id, node_id, task_id, video_url, status, cost, created_at)` + 索引

#### 1.3 单机多标签页并发安全
- **位置**：`runner.mjs:431` 的 `activeByWf`
- **做法**：保持「同流 1 run」，但把状态从纯内存改成「内存 + DB 兜底」；同 wf 已有 run 时返回 409 并**带上当前 runId**，前端一键跳转查看，而不是只报错
- **收益**：多标签页/多窗口场景不会一脸懵

---

### 批次 2 · 上游解耦：provider 注册表（约 5 人天，🔴 高价值，架构级）

**目标**：把「秘塔 H3」从代码里抽成一个可替换的协议实现。这是天花板最高的一步。

**核心设计**：

```
lib/providers/
  index.mjs       注册表：get(id)、list()、按 config 的 provider 字段取用
  metaso-h3.mjs   现有秘塔实现（把 PROVIDER 常量 + gateway 路径 + 参数约束搬进来）
  minimax.mjs     官方 /v2（与秘塔同构，先做参数差异）
  capability.js   能力旗标：supportsRegen / supportsUrlMedia / framesVsRef / ratios / durationRange
```

- **修改** `server.mjs`：`gateway()` 不再拼死路径，改为 `provider.request(op, body)`；新增 `GET /api/providers` 回能力旗标
- **修改** `web/src/graph/model.js`：`PROVIDER` 常量改为从 `/api/providers` 拉，`validateGraph` 按能力旗标校验；节点语义（20 类）保持不动
- **收益**：
  - 换平台成本从「改代码 + 重新构建」降到「改一个配置项」
  - 为接自建网关 / 第三方 OpenAI 兼容视频接口铺路
  - 「上游改参数就崩」的风险被隔离在单个 provider 文件里

**风险**：`model.js` 是节点唯一扩展点，动它要极其克制——只搬「平台相关约束」，**绝不碰节点定义**。用户表里的 `PROVIDER.framesVsRef` 被 `AGENTS.md` 列为硬约定，需同步更新文档。

**备选方案**：不做注册表，只把 `PROVIDER` 常量抽成 `config.json` 里的 `provider` 覆盖项。工作量减半（🟢），但换平台仍需改代码，只是不用重新构建。**适合你短期内只有一家上游的场景。**

---

### 批次 3 · 并发与批量出片（约 4 人天，🟡 中）

- **做法**：
  - 新增 `lib/queue.mjs`：单机内存队列 + 可配置并发度（默认 1，避免网关限流）
  - `POST /api/run` 支持入队，`GET /api/queue` 看排位
  - **批量出片**：`POST /api/run { matrix: { varName: [v1, v2, v3] } }` → 笛卡尔积生成 N 个 run（复用现有 `text.vars` 的 `{{key}}` 替换）
- **依赖**：建议在批次 2 之后做（provider 化才能判定上游并发耐受度）
- **收益**：从「一个个流串行点」变成「一次配 10 条，队列慢慢跑」

---

### 批次 4 · 音频能力（约 3 人天，🟡 中，**取决于批次 0 实测**）

- **若产物无音轨**：加 `audio.tts` 节点（接 TTS 接口，或本地 Edge TTS 走 npm 包），`video.concat` 时用 `ffmpeg amix` 混音
- **若产物有音轨**：只需补「保留原音」选项 + 混音时的音量平衡
- **新增**：`lib/media-tools.mjs` 加 `muxAudio(video, audio, opts)` / `mixTracks(list, opts)`
- **收益**：消掉「输出无声、必须后期配」这条最影响成片可用性的限制

---

### 批次 5 · 剪辑最小加工（约 6 人天，🟡 中，可选）

**定位**：只做成片交付前的最后 1 公里，**不做时间轴**。

- 新增处理节点：`video.subtitle`（SRT 烧录 / 软字幕）、`video.audio`（BGM 混音 + 淡入淡出）、`video.clip`（按秒截取）、`video.transition`（xfade 简单转场）
- 全部经 `lib/media-tools.mjs`，与现有 `toLocalPath` 归一逻辑保持一致
- **收益**：产出可「直接发」的视频，而不是半成品

---

### 批次 6 · 模板与分享生态（约 3 人天，🟢 低）

- 复用现有 `lib/bundle.mjs` 的 zip 能力：把「一张完整画布 + 预设参数」存为模板
- 内置模板从 13 条文本预设升级为**画布模板**（真正的图，不只是提示词）
- `GET /api/templates` 列表、一键「新建自模板」
- **收益**：直接消掉「生态小、模板少」的相对劣势（对比剪映的海量模板）

---

### 批次 7 · 降低上手门槛（约 4 人天，🟡 中）

- **首启向导**：检测无 `config.json` → 引导页填 Token → 一键试跑 5 秒样例（把「配完就跑通」的成就感前置）
- **一键启动器**：`start.bat` / `start.sh`，自动检测 Node 版本、自动 `npm install` + `build`
- **桌面壳（可选）**：Electron / Tauri 打包——注意 `AGENTS.md` 已记录「桌面壳里 `window.prompt` 不工作」，说明作者已在考虑这条路；本项目 v0.3.0 已把所有原生弹窗换成 `wb-modal`，正是为它铺路

---

### 批次 8 · 格式互通（约 3 人天，🟢 低优先级）

- ComfyUI 工作流 JSON → 本项目的**单向**转换器（节点映射天然有限，只做常见生成链）
- **不建议优先做**：除非确有需求，收益窄、维护成本高

## 4. 推荐执行顺序

```
批次 0（0.5d，先验） ─┬─→ 批次 1（5d，地基） ──→ 批次 3（4d，并发）
                      └─→ 批次 2（5d，provider 解耦） ──→ 批次 4（3d，音频）
                                                            └→ 批次 5（6d，剪辑加工，可选）
        批次 6（3d，模板）· 批次 7（4d，上手门槛）—— 可随时插入，互不阻塞
        批次 8（3d，格式互通）—— 建议压到最后或不排
```

**如果只能先做一件事**：
- 想**立刻见效** → 批次 0 + 批次 1（5.5 人天，消掉 3 条已知限制）
- 想**抬高天花板** → 批次 0 + 批次 2（5.5 人天，把自己从单一上游里解放出来）

**我的建议**：先做 **批次 0 + 批次 1**。理由是它不动架构、可视收益明确，而且批次 0 的实测结论会反过来修正批次 2/4 的设计——先花这半天，能省后面返工。

## 5. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| 批次 2 动 `model.js` 打乱节点定义 | 全画布行为回归 | 中 | 只搬平台约束，不碰节点语义；改完跑现有 20 节点校验回归 |
| 重试逻辑误用在新任务创建上 | **重复扣费** | 中 | 白名单式：只对 GET/查询开启；POST 一律不重试 |
| URL 素材改造后网关不认 | 阶段白做 | 中 | 批次 0 先实测，结论不支持则退化为「优化 base64 内存峰值」 |
| 新增表与 `KEEP_PER_WF` 语义冲突 | 老数据查不到仍存在 | 低 | `run_outputs` 独立保留策略，不受 run 清理影响 |
| 引入外部服务依赖 | 破坏「装完就跑」优势 | 中 | 硬约束：任何新依赖必须纯 npm 且可选启用 |
